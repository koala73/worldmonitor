# Golden-baseline env pinning missed a module-load-captured constant

## Problem

Issue #7728 (koala73/worldmonitor; implemented by PR #7732, merged 2026-09-05T15:54:36Z — verified live via `gh pr view` at extraction time) added an independent golden CRI output baseline: a committed artifact of Country Resilience Index score/ranking bytes plus a byte-identity non-regression test (`tests/resilience-cri-golden-baseline.test.mts`), generated by the frozen harness in `scripts/generate-cri-golden-baseline.mts`.

The harness pinned four `RESILIENCE_*` feature flags by writing them into `process.env` (exported as `GOLDEN_ENV_FLAGS`, applied via `applyGoldenEnvFlags()`, called from the test's `before()` hook and from the generator's `main()`). The comment on `GOLDEN_ENV_FLAGS` originally claimed these four were the only `RESILIENCE_*` env reads in the scoring path, so pinning all four pins the flag-dependent behavior.

That claim was false. A fifth read exists and is different in kind: `server/worldmonitor/resilience/v1/_shared.ts:50-51` captures the flag at **module load**:

```ts
export const RESILIENCE_SCHEMA_V2_ENABLED =
  (process.env.RESILIENCE_SCHEMA_V2_ENABLED ?? 'true').toLowerCase() === 'true';
```

This is a top-level `const`, evaluated exactly once when the ES module graph is imported — before any test `before()` hook or generator `main()` body runs. Writing `process.env` afterwards cannot retroactively change a value that has already been captured; the constant is frozen for the process lifetime. The captured const gates the cache-formula tag (`_shared.ts:431`, inside `currentCacheFormula()`, exported as `getCurrentCacheFormula()`).

A multi-perspective review in the authoring session caught it: four reviewer personas, one independent cross-model adversarial pass (Codex), and a docs/solutions learnings scan. The scan flagged the "only four reads" claim as a live violation of the sibling learning `docs/solutions/conventions/hermetic-against-the-env-file-is-not-hermetic-against-the-environment.md`, whose core principle is that *a hermeticity guard covers the acquisition path it intercepts, and says nothing about the others*. Env pinning covers call-time reads; it says nothing about module-load captures.

## Symptoms

- With `RESILIENCE_SCHEMA_V2_ENABLED=false` in the ambient shell, the golden **bytes** test still passed — the byte path (`scoreAllDimensions` + `buildDimensionList`/`buildDomainList`/`buildPillarList` + `penalizedPillarScore`) never reads the captured const.
- The failure surfaced one assertion downstream, in the cache-identity test: `artifact.formula` (`'pc'`) no longer matched live `getCurrentCacheFormula()` (`'d6'`), and the failure message was the regeneration hint ("if this is an intentional CRI methodology change, regenerate with `npm run freeze:resilience-cri-golden`…") — **wrong advice**. The bytes were fine and there was nothing to regenerate; the ambient environment was the problem.
- The same commit could pass on one machine and fail on another (developer shell vs CI) with no code difference — inexplicable, env-dependent test behavior.
- The harness comment that asserted exhaustiveness gave false confidence: the claim was prose, not anything mechanically enforced.

## What Didn't Work

**Pinning `process.env` after import.** `applyGoldenEnvFlags()` writes the four flags into `process.env` at test-`before()`/generator-`main()` time. By then, `import` of `_shared.ts` has fully evaluated and the module-load line has captured the ambient value. ESM module evaluation is not deferred and is not re-run per call; a post-import env write only reaches code that reads the environment **at call time**.

The trap is subtle because the same pin genuinely works for the other four flags. Those are read inside per-call helper functions — `isPillarCombineEnabled()`, the energy-v2 helper, the fin-sys-exposure helper, and the education helper — so every scoring call re-reads `process.env` and observes the pin. The distinction is **capture time** (module load vs call time), not the variable name. An exhaustiveness claim that enumerates variables without classifying their read timing is structurally incomplete.

Empirically reproduced (Codex adversarial pass and locally): ambient `RESILIENCE_SCHEMA_V2_ENABLED=false` → bytes green, formula-metadata assertion red, with a "regenerate the baseline" message that was actively misleading.

## Solution

All changes in PR #7732 (merged 2026-09-05); every test green and the CI gate passed before merge.

**1. Fail fast on the imported const.** `assertFrozenScorerDefaults()` (`scripts/generate-cri-golden-baseline.mts`) imports the module-load constant itself and refuses to proceed on an unexpected captured value:

```ts
export function assertFrozenScorerDefaults(): void {
  if (!RESILIENCE_SCHEMA_V2_ENABLED) {
    throw new Error(
      'RESILIENCE_SCHEMA_V2_ENABLED was captured as false from the ambient environment. ' +
        'The golden CRI harness requires the default (unset RESILIENCE_SCHEMA_V2_ENABLED in your shell or CI); ' +
        'unset it and re-run.',
    );
  }
}
```

Importing the binding is exact — it is the same value the scorer uses — and the error message carries the actual cause and the remediation ("unset it and re-run"), not a prescription to regenerate.

**2. One choke point so both harness paths inherit the guard.** `applyGoldenEnvFlags()` calls `assertFrozenScorerDefaults()` first. The test's `before()` calls `applyGoldenEnvFlags()` and the generator's `main()` does too, so generation and comparison both fail before any scoring runs — the two paths can never disagree on the const's interpretation.

**3. Keep env pins for the genuinely dynamic reads; document the split.** `GOLDEN_ENV_FLAGS` still pins the four per-call flags. The corrected comment states the distinction explicitly: those four are "the only DYNAMIC (read-per-call) RESILIENCE_* env reads", while `RESILIENCE_SCHEMA_V2_ENABLED` "is captured at `_shared.ts` module load (before any env pinning can apply), so it cannot be pinned here — `assertFrozenScorerDefaults()` below fails fast on it instead."

**4. Mechanical exhaustiveness guard.** `tests/cri-golden-baseline-guards.test.mts` replaces the prose claim with a proof, re-derived on every test run:

```ts
it('pins every RESILIENCE_* env-read occurrence to its file and capture timing', () => {
  const reads: ResilienceEnvRead[] = [];
  for (const entry of readdirSync(SCORER_TREE_DIR, { recursive: true, withFileTypes: true })) {
    if (!entry.isFile() || !entry.name.endsWith('.ts')) continue;
    const filePath = path.join(entry.parentPath, entry.name);
    reads.push(...collectResilienceEnvReads(filePath, readFileSync(filePath, 'utf8')));
  }
  assert.deepEqual(reads.map(formatEnvRead).sort(), EXPECTED_ENV_READS);
});
```

It parses every `.ts` file in `server/worldmonitor/resilience/v1`, records each `process.env.RESILIENCE_*` occurrence, and classifies the occurrence as call-time or module-load from its AST ancestors. A top-level immediately invoked function inherits module-load timing from its call site; an IIFE inside a deferred function remains call-time. Repository paths are normalized to `/` on every operating system. The expected multiset pins the variable, file, and capture timing. A separate assertion requires the call-time variable set to match `GOLDEN_ENV_FLAGS`. Moving a known call-time flag to module scope, adding another occurrence, or adding a new flag now fails with the two sanctioned remedies.

**5. Corollary hardening in the same PR — one shared harness module and a timestamp-free artifact.** The generator exports the frozen harness (clock, reader, byte computation) and the test imports it, so the generator and the test cannot compute different bytes from drift. The artifact carries no wall-clock timestamp (`frozenClockIso` is the pinned constant, `inputFixture.capturedAt` is the fixture's committed capture date), so regenerating on the same commit is a git no-op (confirmed during the authoring session by hashing two consecutive generations).

## Why This Works

- **The fix targets the actual capture mechanism.** A module-load `const` is fixed at import time; the only reliable way to know and control it is to read the exported binding — the same object the scorer dereferences — and refuse to proceed when it is not the intended default. Import-and-assert has no ordering hazard: the value checked is exactly the value used, for the whole process lifetime.
- **Each hermeticity mechanism matches its target's read timing.** Module-load capture → import the binding and fail fast. Per-call read → `process.env` writes in hooks. The original bug was applying mechanism #2 to a target that only mechanism #1 can reach.
- **Failure moves earlier and gets attributed correctly.** Instead of a delayed failure in a downstream assertion whose message blames the scorer and advises regeneration, the guard fires before any scoring runs, with the cause (ambient env) and the fix (unset it) in the message.
- **The invariant became mechanical.** "All env reads and their capture timing are accounted for" is now re-derived by an AST scan on every run. A new read, an extra occurrence, or a move between call time and module load fails loudly instead of silently widening the golden bytes' ambient sensitivity.
- **Shared harness + timestamp-free artifact close the sibling failure classes.** One implementation imported by both generator and test eliminates byte-drift between them; a timestamp-free artifact makes the sanctioned "regenerate" flow idempotent, so the advice is safe to follow when it is actually correct.

## Prevention

- **Treat any "we pin/cover all the env reads (or inputs)" claim as unverified until mechanically enumerated.** Write the source-grep (or AST sweep) that lists every read and asserts membership in the covered set. Prose comments about exhaustiveness are the failure surface, not the protection.
- **Classify read timing before choosing a hermeticity mechanism.** Grep the imported module graph for top-level `const X = …process.env…` patterns (or exported env-derived consts). For captured values: import the binding and fail fast on it (or restructure to a factory that takes config explicitly, or `import()` dynamically after pinning). For per-call reads: `process.env` writes in setup hooks are sufficient.
- **Post-import env writes can only affect call-time reads.** A constant captured at module load is immutable for the process lifetime; no hook ordering fixes it.
- **Gate prescribed actions behind preconditions that diagnose the environment.** An assertion whose message says "regenerate" should only fire when regeneration is the actual remedy. When an environmental precondition (ambient env drift) can make a legitimate assertion fire spuriously, verify that precondition first and report it, as `assertFrozenScorerDefaults()` does.
- **Metadata derived from env is as env-sensitive as the bytes it describes.** A golden artifact's `formula` field is computed from the same flags family as the bytes but via a different variable (`getCurrentCacheFormula()` reads the captured const; the bytes don't). Pin and verify both, and never treat a passing byte-comparison as certifying metadata consistency.
