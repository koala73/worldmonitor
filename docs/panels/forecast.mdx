The **AI Forecasts** panel (internal id `forecast`) surfaces forecasts produced by WorldMonitor's forecasting pipeline. Each forecast is a structured prediction with a probability, a domain classification, a time horizon, and supporting signals; the panel exposes two axes of filtering (domain and macro-region) so you can home in on the slice that matters to you.

## What the panel shows

A list of active forecasts, filtered by two pill rows:

### Domain filter

`All` / `Conflict` / `Market` / `Supply Chain` / `Political` / `Military` / `Cyber` / `Infra`

### Region filter

`All Regions` / `MENA` / `East Asia` / `Europe` / `South Asia` / `Africa` / `LatAm` / `N. America`

Forecasts whose region does not classify (unknown or `global`) only appear under **All Regions**. The panel's minimum-probability floor is `0.1` (10%) — predictions below that threshold are suppressed from the panel view.

Each forecast row shows the prediction text, the event probability, the domain (color-coded), the time horizon, and a compact provenance trail. Deep-simulation path confidence is shown separately as confidence, not as event probability.

## Calibration & Projection Notes

Forecast probabilities come from deterministic, rule-based signal detectors in `scripts/seed-forecasts.mjs`, with an optional prediction-market blend when a matching market anchor exists. LLM calls do not set the numeric probability. They generate the narrative scenario, case-file, branches, and perspective text around the already-scored forecast. The default source-backed LLM routes in the seeder are OpenRouter `deepseek/deepseek-v4-flash` (primary, reasoning disabled), then fixed free OpenRouter fallbacks `google/gemma-4-26b-a4b-it:free` and `nvidia/nemotron-3-super-120b-a12b:free`. One tracked exception: the critical-signals extraction stage contributes signal strength/confidence into the deterministic scoring of state-derived (market/supply-chain) forecasts, so that stage stays pinned to OpenRouter `google/gemini-2.5-flash` (see issue #4963).

Forecast probabilities are market-calibrated only when the seeder can match the forecast to a prediction-market anchor that asks the same kind of question. In those cases the `calibration` object includes the market title, market price, drift, source, the pre-blend `internalProbability`, and the post-blend `marketBlendedProbability`, and the displayed probability is blended with that market anchor. Forecasts with `calibration: null` are internal/legacy estimates derived from WorldMonitor signal rules rather than externally market-calibrated probabilities.

The seeder also computes horizon projections (`24h`, `7d`, `30d`) for each forecast. They are not probabilities, and they are not published: payloads generated after 2026-10-07 ([issue #8967](https://github.com/koala73/worldmonitor/issues/8967)) omit the `projections` field, so the API and MCP stop returning it once the first such run replaces the cached forecasts. The seeder keeps them only in its internal forecast history, where horizon scoring reads them. Each value comes from a fixed, hand-set domain curve in `scripts/seed-forecasts.mjs` (`computeProjections`). The forecast probability is divided by the curve's multiplier at an anchor horizon, multiplied by the multiplier for the target horizon, and then clamped to a 1% floor and 95% cap (`0.01` / `0.95`). The anchor is the forecast's own emitted horizon, except for market forecasts, which anchor on the curve's strongest multiplier so a 30-day market emission does not inflate the 24-hour value. For a forecast whose own resolution spec is a point-in-time hard contract (`at-deadline`, today the supply-chain chokepoint and GPS-jamming families), each projection other than the forecast's own horizon gets a resolution window in the outcome ledger, keyed `<id>@<deadline>@<horizon>`, frozen at the probability it was first emitted with, and read from the nearest feed sample inside the stored tolerance (one resolver cycle, capped at half the horizon) around the horizon deadline. The resolutions seeder reports them per horizon in a separate `projections` section of the stored scorecard, never pooled into the headline and withheld until a horizon reaches the minimum sample. Every other projection (judged, within-horizon, or settlement-dated specs) is unscored with a stated reason. Each published forecast's `scoredHorizons` field names the horizons that have a registered scoring window. The projection values, scoring windows and per-horizon results are not published.

The panel names the horizons listed in `scoredHorizons` on an "Also scored at" line under the forecast title. The headline probability is graded at the forecast's own horizon, so the line lists only the extra horizons. The panel shows no projection values, and the narrative prompt does not receive them. The prompt still carries the forecast probability, which can equal an anchor-horizon projection, so a matching percentage in scenario or case text is not evidence that a projection was used. Per-horizon scoring is tracked in [issue #7075](https://github.com/koala73/worldmonitor/issues/7075).

The `GET /api/forecast/v1/get-forecasts` response includes `degraded`, `stale`, and `error` fields so clients can distinguish a backend/cache outage from a healthy empty forecast set.

Panel id is `forecast`; canonical component is `src/components/ForecastPanel.ts`.

## How you reach it

- **Cmd+K**: type *forecast*, *ai forecast*, or *predictions ai*. The command palette label is "AI Forecasts" even though the internal panel id is `forecast`.
- **Availability by variant**: registered and enabled by default in the **full/geopolitical** variant only. Not present in the tech, finance, commodity, or happy variants. Source: `FULL_PANELS` in `src/config/panels.ts`.

## Data sources

Primary RPC: `GET /api/forecast/v1/get-forecasts`. The panel also consumes adjacent RPCs for the richer deep-simulation surface:

- `GET /api/forecast/v1/get-simulation-package` — the most recent simulation inputs bundle.
- `GET /api/forecast/v1/get-simulation-outcome` — the most recent simulation result. Outcomes auto-refresh on the deep-forecast cron cadence (~hourly); each cycle enqueues a worker task after writing the simulation package.
- `POST /api/forecast/v1/trigger-simulation` — starts a fresh simulation run outside the cached cron output. Usually unnecessary — outcomes already auto-run each cron cycle.

The forecasting pipeline runs as a Railway cron that pulls recent conflict, intelligence, markets, and supply-chain signals, runs them through the forecasting model, and writes the aggregated result at `forecast:predictions:v2` in Redis. Macro-region classification comes from `shared/forecast-macro-regions.js`.

## Scoring and calibration

Published forecasts are capped and deduplicated before they reach the panel:

| Rule | Cap |
| --- | --- |
| Forecasts per situation | 3 |
| Forecasts per situation/domain pair | 2 |
| Forecasts per family | 4 |
| Forecasts per family/domain pair | 2 |
| Target published count | 10-14 |
| Conflict base detector probability ceiling (before velocity spike) | 0.90 |
| UCDP conflict-zone gate floor at 10 events (before velocity spike) | 0.35 |
| UCDP conflict-zone base probability ceiling (before velocity spike) | 0.85 |
| Conflict velocity-spike override ceiling | 0.99 |
| Market probability ceiling | 0.85 |
| Supply-chain / maritime probability ceiling | 0.85 |
| GPS supply-chain detector probability ceiling | 0.60 |
| Political probability ceiling | 0.80 |
| Military probability ceiling | 0.90 |
| Infrastructure probability ceiling | 0.85 |
| Cyber probability ceiling | 0.72 |

A market anchors a forecast only when all of these hold:

- The market title names the forecast's own region: the region name or its country keywords. A shared macro-region tag or a neighbouring country from the entity graph does not count, so a Syria forecast does not anchor to a market about Iran.
- The market title resolves on the event class that `MARKET_ANCHOR_EVENT_CLASSES` in `scripts/seed-forecasts.mjs` declares for the forecast's domain. Conflict and military escalation forecasts need a strike, attack, invasion, offensive, clash, or war market. A trade war or tariff war does not count. De-escalation forecasts need a ceasefire, truce, or peace-deal market. Political instability forecasts need a resignation, ouster, impeachment, coup, snap election, or unrest market; a market that only asks who will hold an office does not qualify. Supply-chain forecasts need a strait, canal, blockade, shipping, or transit market. Infrastructure forecasts need an outage, blackout, grid, or pipeline market. Market forecasts need a commodity or macro price market that also shares a title term with the forecast.
- The market settles inside the forecast's own window. The forecast deadline is emission time plus its horizon (`24h`, `7d`, or `30d`). The market's `endDate` must fall between emission and the deadline plus the larger of 7 days and the horizon (`MARKET_ANCHOR_MIN_SETTLEMENT_SLACK_MS`). A 7-day forecast therefore accepts a market settling within 14 days of emission, and a 30-day forecast accepts one settling within 60 days. A market that settles much later prices risk over a longer period than the forecast claims, so its price is not an estimate of the same event. A market with no settlement date does not anchor. On the 2026-10-06 market universe every same-subject, same-event-class market settled at the end of 2026 or later, so no forecast was market-calibrated.

A domain or title family without a registry entry gets no anchor. Cyber forecasts and GPS interference forecasts are excluded this way. A cyber forecast asks about threat activity in its country, and no market asks that question. The existing price, liquidity (`volume >= 5,000`), YES-direction, and region-tag filters still apply. This rule exists because region overlap alone let unrelated long-dated markets, such as a Taiwan invasion market or a presidential succession market, calibrate cyber-concentration forecasts (issue #7071).

When a market anchor applies, the final probability is blended as `0.4 * market_probability + 0.6 * internal_probability` and then capped at the domain ceiling. The `calibration` object records the market title, market price, source, `drift` (internal probability minus market price), `internalProbability` (the pre-blend value), and `marketBlendedProbability` (the post-blend, post-cap value, equal to the published probability). The history snapshots and the resolution ledger carry the same fields, so a later audit can recompute the blend without reconstructing it from drift.

Market-bucket scenario calibration is an editorial calibration layer in `scripts/seed-forecasts.mjs`, not a learned market model. It biases how market-context simulation states contribute to forecast pressure and confidence so that direct energy/freight transmission receives more lift, broad macro buckets stay moderate, and defense repricing is damped unless the evidence is strong.

| Bucket | Simulation bias: confirmation / pressure / edge / contradiction | State calibration: edgeLift / macroLift / confidenceLift / dampener | Rationale |
| --- | --- | --- | --- |
| Energy | `0.20 / 0.12 / 0.10 / 0.14` | `0.08 / 0.14 / 0.05 / -` | Strong direct route, commodity, and macro pass-through. |
| Freight | `0.18 / 0.12 / 0.10 / 0.14` | `0.09 / 0.12 / 0.04 / -` | Shipping-cost shocks are treated as high-signal supply-chain pressure. |
| Sovereign risk | `0.17 / 0.11 / 0.09 / 0.15` | `0.07 / 0.10 / 0.04 / -` | Macro stress matters, but confirmation still needs country/market evidence. |
| Rates / inflation | `0.16 / 0.10 / 0.08 / 0.16` | `0.06 / 0.12 / 0.05 / -` | Policy and inflation transmission is broad but less event-specific. |
| FX stress | `0.15 / 0.09 / 0.08 / 0.14` | `0.05 / 0.10 / 0.04 / -` | Currency pressure is allowed to lift risk, with moderate confidence. |
| Semis | `0.13 / 0.08 / 0.09 / 0.12` | `0.04 / 0.04 / 0.02 / -` | Semiconductor shocks need targeted infrastructure or shipping evidence. |
| Crypto / stablecoins | `0.11 / 0.07 / 0.08 / 0.12` | `0.03 / 0.05 / 0.02 / -` | Digital-asset stress is useful context but gets a lighter macro lift. |
| Defense | `0.08 / 0.04 / 0.05 / 0.10` | `-0.03 / 0 / -0.03 / 0.12` | Defense signals are intentionally damped to avoid over-reacting to noisy security headlines. |

The conflict and UCDP conflict-zone rows are base detector caps. UCDP conflict-zone counts begin at the 10-event publish gate with a `0.35` base probability and ramp to the `0.85` base cap at 100 events. When the matching EMA risk score has `velocitySpike`, the seeder adds a `+0.08` probability override after the base cap and clamps the result to `0.99`.

Defense state calibration has additional direct-confirmation terms outside the table: each unit of direct `defense_repricing` confirmation adds `+0.12` pressure and `+0.08` confidence. When that direct defense confirmation is absent, pressure subtracts the table-driven `dampener` (`0.12`) and confidence subtracts a separate `0.04` absence penalty.

The unscored horizon projections are expanded to 24h, 7d, and 30d with these hand-set domain curves. The multipliers are editorial priors, not fitted values. Market projections use the curve's peak multiplier as the anchor; other domains use the forecast's emitted horizon:

| Domain | 24h | 7d | 30d |
| --- | ---: | ---: | ---: |
| Conflict | 0.91 | 1.00 | 0.78 |
| Market | 1.00 | 0.58 | 0.42 |
| Supply chain | 0.91 | 1.00 | 0.64 |
| Political | 0.83 | 0.87 | 1.00 |
| Military | 1.00 | 0.91 | 0.65 |
| Cyber | 1.00 | 0.78 | 0.40 |
| Infrastructure | 1.00 | 0.50 | 0.25 |

Trend is serialized as a string, not an enum. The current values are `rising`, `falling`, and `stable`, based on a +/- `0.05` probability delta versus the prior forecast snapshot.

## Shadow bet-engine evaluation lane

World Monitor also runs a **shadow-only** forecasting lane at `forecast:bets:history:v1`. It never writes `forecast:predictions:v2`, so its bets do not appear in the AI Forecasts panel. The purpose is to measure candidate generation methods against resolved outcomes before allowing them into the user-facing forecast stream.

The lane now includes a dedicated geopolitical prediction-market family:

- It selects liquid geopolitical markets whose settlement is 2–210 days away. The general market family retains the shorter 2–45 day window.
- The two families form a disjoint partition by market slug, so the same venue market cannot become two separate bets.
- Geopolitical candidates rank first for the optional ensemble stage, but the attempt budget reserves room for faster-resolving energy, commodity, general-market, and macro families.
- Identity and settlement use the venue slug rather than the mutable title. The hard resolution spec reads the settlement feed at the market deadline and resolves whether the YES price crossed 50%.
- Results remain tagged `generationOrigin: "bet_engine"` so the scorecard can compare that lane with the canonical forecast generator instead of mixing their records.

Each shadow bet retains its empirical or thin-history `baselineProbability`. When `FORECAST_BETS_ENSEMBLE=1` is explicitly enabled, a bounded three-pass LLM ensemble may replace the working probability for top-ranked new attempts while leaving the baseline attached for Brier-score comparison. The ensemble is off by default; partial passes are labeled `ensemble_partial` and are eligible for a later upgrade rather than being treated as a completed ensemble.

This separation is deliberate: prediction-market liquidity is useful calibration evidence, but shipping a new family directly into the panel before it accumulates settlement history would confuse implementation completeness with demonstrated forecast skill.

## Resolution spec

Every published forecast carries a **resolution spec** — a machine-checkable contract that defines what "came true" means at resolution time. The spec is either `hard` (auto-resolvable by comparing a metric from the same WorldMonitor feed the detector scored from) or `judged` (a resolution question for a later LLM judge, still with a hard deadline). The deadline is always present, encoded in epoch milliseconds: emission time plus the forecast's stated horizon — except prediction-market forecasts, which resolve at the market's own end date when it has one.

**Hard specs** apply to forecasts with clean metric backing:

- **Conflict**: UCDP conflict-event counts in the forecast's region.
- **UCDP zones**: UCDP conflict-zone event counts.
- **Market**: commodity-future price moves measured from the emission-time baseline.
- **Prediction-market**: the spec still carries the market's end date, but the resolver seals it as VOID with reason `market_price_not_outcome`. Its feed, `prediction:markets-bootstrap:v1`, lists only open markets and clips `yesPrice` to 10 to 90, so a read at the end date is the crowd's price, not the outcome (issue #5233).
- **Supply chain**: the chokepoint's disruption score on the deadline reading. A route whose standing threat score is below the feed's red boundary resolves YES at a score of at least 50 (`CHOKEPOINT_DISRUPTED_MIN_SCORE`, the boundary `scoreToStatus` calls red). The supply-chain detector emits at that boundary, recorded as `rule: disrupted` with a `ruleVersion`. A state-derived freight forecast attaches the same contract at any score, on the most disrupted chokepoint in its sea. Hormuz and Kerch carry a fixed war-zone base of 70, which is already red, so a reading cannot fall through 50. Their contract is a score above that base (`rule: above_fixed_base`). Pending rows move to the current contract before they resolve and keep the earlier threshold as `supersededThreshold`. Resolved rows keep the threshold they were graded on (issues #8990 and #9033).
- **GPS interference**: the number of gpsjam.org hexes inside the shipping-zone box on the snapshot dated on or after the deadline day. The forecast resolves YES when the zone still holds at least 3 hexes, the same floor at which the detector emits it. The spec records this as `rule: persistence` with a `ruleVersion`. Pending rows written under the earlier emission-count threshold move to this rule before they resolve, and keep the old value as `supersededThreshold` (issue #8990).
- **Infrastructure**: reported outage events for the forecast's country.

**Judged specs** apply to forecasts in domains where signal-to-outcome mapping is editorial or composite:

- **Political**: regime stability, negotiations, policy shifts.
- **Military**: posture transitions, deployment patterns.
- **Cyber**: attribution and impact severity.
- **State-derived** forecasts whose bucket has no feed metric at emission. Energy forecasts resolve on the `CL=F` price, and supply-chain freight forecasts resolve on a chokepoint score.
- Hard-family forecasts that cannot derive a finite threshold despite their domain (e.g., a market forecast with no tradeable anchor).

The resolution spec does not change which forecasts are published or their order — it only *adds* machine-checkable ground truth to each forecast, the substrate for a future public track record that scores forecasts against what actually happened.

## Refresh cadence

The seeder runs approximately **hourly**. The key is allowed up to **90 minutes** in `api/health.js` (`maxStaleMin: 90`) before the health surface escalates.

## Resolution & track record

Published forecasts carry machine-checkable resolution specs. A daily resolver pre-registers those specs into `forecast:resolutions:v1`, samples hard-source metrics until their deadlines, then resolves each published forecast to YES, NO, or VOID with evidence. The derived `forecast:scorecard:v1` reports Brier score, log score, calibration buckets, VOID rate, publication coverage, and market-anchor skill. Judged specs are tracked as pending for a fast-follow judge and are excluded from the first hard-source scorecard until resolved.

The scorecard also reports skill against the actual rate: always forecasting how often the same forecasts came true in the window. The Brier skill score is `1 - Brier / p(1-p)`, where `p` is that rate, computed on exactly the same rows. Its 95% interval comes from a bootstrap that resamples whole forecast families, and `/accuracy/` calls a cohort better or worse only when that interval lies wholly above or below 0. A forecast family is one forecast id; its windows share a question and an outcome, so a family counts once. That only approximates independence: on 2026-10-07, 42 of 603 question texts in the ledger appeared under more than one forecast id. A cohort or domain is scored once it has at least 30 forecast families, with at least 5 that came true and 5 that did not; a family with both outcomes counts on both sides. The calibration refit (#9027) needs 12 of each, because a fitted map must beat the identity map, while a score only has to be stable. Below the minimum the scorecard still reports the reading, flagged as a small sample, and publishes no domain score.

State-derived market forecasts in the `sovereign_risk`, `rates_inflation` and `fx_stress` buckets are not published, because no feed can check them (issue #5234). Their earlier rows stay in `forecast:resolutions:v1`, but the scorecard leaves them out of every figure it reports, including the VOID rate. The resolver seals their open rows as VOID with reason `withheld_unpublished` and calls no judge. State-derived `energy` and `freight` forecasts are still published. They resolve on a price or chokepoint feed when that feed has a matching value at emission, and go to the judges otherwise.

Before the fix for issue #5233, the resolver read `cyber:threats-bootstrap:v2` and `infra:outages:v1` as raw seed envelopes (`{_seed, data}`), found no records in them, and scored every cyber count and every outage presence check as 0. Those NO outcomes measured the reader, not the world. The resolver now unwraps the envelope before it reads any feed, and the emission-time extraction check reads the same unwrapped view. Each run seals the rows resolved before the fix with that zero reading as VOID with reason `resolver_envelope_bug`. It keeps their original outcome and evidence under `supersededOutcome` and `supersededEvidence`, and records when it voided them in `voidedAt`. A row already corrected is left unchanged, and a zero read by the fixed resolver keeps its outcome. While voided rows are in the rolling window, the scorecard methodology states how many there are. Price checks on `prediction:markets-bootstrap:v1` hit the same reader and sealed as VOID with `no_establishable_metric`.

The unwrap exposed a second problem in the cyber feed. Only AbuseIPDB and URLhaus records carry a country, and the feed lists each for less than a day. A 7-day count read once a day therefore depends on how many hours before the read the deadline fell. One claim read 112 threats 1 hour after its deadline and 0 at 18 hours. Cyber forecasts are now judged, like infrastructure and military, and each run moves pending hard cyber rows to the judged lane. The news archive held few items on these subjects, so judged cyber rows are held out too. When one comes due, the resolver seals it as VOID with reason `judged_evidence_unreliable` and calls no judge. The constant `CYBER_JUDGING_HELD` lifts the hold once the judges' evidence is fixed (#8990). The calibration map's code version moved to `forecast-calibration-pav-v2`, so the map is refitted without the voided rows.

### Windows and the scored probability

The resolver keeps one ledger window per question. A window is keyed `<id>@<deadline>` and covers emissions from its `generatedAt` up to its deadline. A market-settlement bet window is the market's own question and covers every later emission of that market, because its deadline follows the venue's close date and can move back before the window's emission once the market closes. A question is the forecast id plus what it asks: the region, and for a judged spec the question text, for a hard spec the metric, operator, window and direction. A bet also counts its threshold, because each bet run asks a new threshold. A detector re-derives its threshold from the live value on every run, so its threshold stays frozen at the window's first emission. When questions of one id share a deadline, the later one gets a `~<hash>` suffix on its key.

The resolver reads the last 200 forecast-history runs and the bet history on every run. An emission that falls inside an existing window for the same question joins that window, whatever the window's status, so re-reading history cannot reopen a resolved window. The resolver does not open a window whose deadline has already passed when it first sees the emission, because it could only read that window from later data.

A window is scored on the probability published at its first emission (`firstSeenProbability`), with the calibration, provenance and ensemble passes that came with it. A later emission of the same question records its probability in `lastSeenProbability` and changes nothing scored. The bet seeder does not re-run the ensemble for a bet whose question already has an open window that covers the current run. A bet window that opened on the base-rate placeholder (`probabilitySource: 'base_rate'`) is scored in the `betEngine` slice, but the slice's base-rate, market and deviation comparisons read only windows that opened on an ensemble (`ensembleCount`).

Before issue #8990, re-reading history reopened windows that had already resolved, and each open window was scored on its last sighting. Each run corrects the rows written before the fix, after the `resolver_envelope_bug` voids. A window whose emission falls inside an earlier window of the same question is a duplicate. It and its horizon windows are sealed as VOID with reason `duplicate_window`, name the window they duplicate in `duplicateOf`, and keep their original status or outcome and evidence under `supersededStatus`, `supersededOutcome` and `supersededEvidence`. A duplicate that was already VOID keeps its reason and gains `duplicateOf`. A duplicate was never a question, so no scorecard count, receipt or card chip includes it. A window whose scored probability differs from its first-seen one, or that the old code saw again, is restored to its first emission with reason `last_seen_probability`, and the values it replaces move under `rescore`. When that emission is still in the history read, the window's provenance, base rate, ensemble passes, market anchor and post-blend lineage come back exactly (`restoredFromHistory`); every bet window's first emission is in the bet history. Otherwise the fields are inferred. The later sighting's passes, anchor and lineage move, and the base rate stays. A first-seen value equal to the base rate marks a window that opened on the placeholder (`probabilitySource: 'base_rate'`). A re-sighted row whose probability did not move keeps its provenance and passes. A row that its first emission confirms is stamped `openingVerifiedAt`, so a later call can no longer mistake it for an overwritten row. Only a call that read history rescores; the resolver's second ingest of a run passes no history and leaves rows as they are. Each run applies the correction again after it opens new windows, because a new window can precede an existing window of its question. A rescored row has no recorded raw value for its first-seen probability, so the calibration fit leaves it out. A corrected row is left unchanged, so re-running the correction changes nothing.

Before issue #8995, the judged lane picked archive items by matching the words of the question template, with no cutoff at the deadline. An audit of the 27 judged YES and NO verdicts sealed that way found 14 unsupported by their own citations and 1 probably wrong. Re-judging needs the archive to cover the last 7 days before the deadline, and every one of those windows closed by 2026-08-23, before the oldest evidence the 15-day archive still holds. Each run therefore seals every judged YES or NO resolved before #8995 reached production (`SUBJECT_GATED_SELECTION_SINCE_MS`, 2026-10-07T14:39Z) as VOID with reason `judged_old_selection`. The row keeps its `resolvedAt`, its original outcome and evidence under `supersededOutcome` and `supersededEvidence`, and records `voidedAt`. The step runs after the window correction, so a duplicate window keeps `duplicate_window`. A voided row is no longer YES or NO, so re-running changes nothing.

A row corrected after its receipt reached R2 (`resolver_envelope_bug`, `duplicate_window`, `judged_old_selection`, `late_read`, `resolver_could_not_read_feed`, a rescore or a late-read re-grade) has its receipt written again. R2 writes run one at a time, at about 450 ms each, inside the run's 150-second fetch phase, so each run rewrites at most `RECEIPT_REARCHIVE_PER_RUN` (50) of these receipts, oldest first. The backlog drains over later runs, and pruning keeps a row until its corrected receipt is written.

### Late reads and missing feeds

A live feed (commodity quotes, chokepoint risk) reports the value at the moment it was fetched, so a point-in-time question (`at-deadline` or `at-endDate`) must be read close to its deadline. The resolver runs once a day (cron `0 6 * * *`), and its runs start between 06:00 and 06:05 UTC, so the first run after a deadline reads the feed within one cycle of it. `LATE_READ_MAX_LAG_MS` is that cycle plus an hour for start jitter. The resolver grades on the first finite reading taken at or after the deadline and within that bound. When no such reading exists once the bound has passed, the row is sealed as VOID: `feed_unavailable` when the feed is missing, `late_read` when the feed holds the metric but read it too late, and `value_source_never_settled` (a price or value) or `no_establishable_metric` (any other metric) when the feed no longer carries the metric. A missed run therefore voids the questions due in the gap instead of grading them on a later price. Feeds that date each reading by its own period or by the venue's adjudication (EIA, FRED, `prediction:markets-resolution:v1`) keep their settlement grace and are not bound by it; when one of them stays missing past that grace, the row is sealed as VOID `feed_unavailable`. A count feed that stays missing for its settlement lag plus `VALUE_SETTLEMENT_MAX_LAG_MS` (10 days) is sealed the same way.

`intelligence:gpsjam:v2` publishes one snapshot per UTC day, dated by its `date` field. A GPS-jamming question grades on the snapshot dated the deadline's UTC day. `seed-gpsjam` runs every 8 hours and day D's snapshot first lands at its 08:00 tick on D+1, so the resolver's 06:00 run on D+2 is the first to hold it. `GPS_JAM_SNAPSHOT_MAX_LAG_MS` is 3 days and 7 hours from the start of the deadline day: that first run, one more cycle for a snapshot published late, and an hour of start jitter. A snapshot dated after the deadline day means the deadline day was replaced before the resolver read it, and the row is sealed as VOID `late_read`. When the bound passes with only older snapshots, the row is sealed as VOID `value_source_never_settled`, or `feed_unavailable` when the feed is missing.

Before issue #8990 no bound applied, and windows the resolver reached days late were graded on that day's price. Each run corrects those rows after the `duplicate_window` voids. A YES or NO row on a live feed whose read landed past the bound is graded again on the first on-time reading that any window of the same metric sampled, or sealed as VOID `late_read` when the ledger holds none. The replaced outcome and evidence move under `supersededOutcome` and `supersededEvidence`. A re-graded row records `regradedAt`, a voided row records `voidedAt`, and `resolvedAt` is unchanged. A corrected row reads on time or is VOID, so re-running the correction changes nothing.

### VOIDs from feeds the resolver could not read

Some feeds held readings while the resolver could not read them, and the rows it sealed in that period carry `no_establishable_metric`, which reads "The feed had no reading for this question". That blames the feed for a resolver fault (issue #9013). Each run relabels those rows `resolver_could_not_read_feed` ("Our resolver could not read this feed correctly"). A row is relabelled when it is a resolved hard VOID with `no_establishable_metric` on one of these feeds, sealed before the first deploy of the resolver that could read it:

| Feed | Resolver fault | Fixed by | Deployed |
|---|---|---|---|
| `intelligence:gpsjam:v2` | read a `hexCount` field the per-hex records never carry | #9003 | 2026-10-07 19:28 UTC |
| `infra:outages:v1` | read the raw seed envelope and found no records | #8986 | 2026-10-07 12:43 UTC |
| `prediction:markets-bootstrap:v1` | read the raw seed envelope and found no records | #8986 | 2026-10-07 12:43 UTC |
| `supply_chain:chokepoints:v4` | read `riskScore`, which the feed publishes as `disruptionScore` | #8893 | 2026-10-06 04:56 UTC |

The outcome and `resolvedAt` are unchanged. The earlier evidence moves under `supersededEvidence`, and `voidedAt` records the relabel, so the R2 receipt is written again. A relabelled row no longer carries `no_establishable_metric`, so re-running changes nothing. VOIDs are outside the accuracy math, so no score changes.

A period feed (EIA, FRED) dates each sample by its observation day, a UTC midnight. A point read on one of them grades on the first sample dated on or after the deadline's UTC day, the same day boundary the settlement gate accepts. Before issue #8990 the selection required a sample at or after the deadline time, so the deadline day's own observation was skipped and the resolver read the live value instead.

### Judged-lane evidence horizon

A judged entry is decided by two independent LLM judges reading the dedicated forecast evidence archive (`forecast:evidence:v1`), and each must cite an archive item by ID with a quote that appears in that item — a judgment with no valid citation can never seal as YES or NO. The judges see up to 32 items, and every item must name the forecast's subject: its region or one of the region's aliases (for example Damascus or Idlib for Syria). The alias table is generated for every country and every region label the forecast emitter can produce (`scripts/build-judged-subject-terms.mjs`). Names that are also common words or places elsewhere (Georgia, Jordan, Chad, Niger, Turkey, Congo) count only beside a disambiguating word such as a capital. Matching is on whole words. The words of the question template never select an item. Items published by the deadline come first, then items that name the subject in the headline, then items that use the forecast domain's event words, then the newest. The evidence window ends 18 hours after the deadline, so reports of deadline-day events can arrive, and an entry is not judged before that. Citing an item published later is impossible, because such items are never shown. The window starts when the forecast was generated, clipped to the oldest evidence the archive still holds, so a 30-day question sees up to 14 days of its horizon. The prompt states the window as served. A NO may rest on absence as well as on proof: both judges may answer NO with basis `absence`, citing the on-subject items they read. Two kinds of check apply. If the archive's coverage bounds do not span the last 7 days before the deadline through the end of the window, the entry stays pending (`archive_incomplete`) and no judge is called, until it reaches its recovery horizon, after which it seals as VOID with `beyond_archive_horizon` (described below). Once coverage holds, each absence-based NO is checked in code, and a judgment that fails is recorded as VOID with the failing condition as its reason: the archive must declare coverage bounds; at least `JUDGED_ABSENCE_MIN_ARCHIVE_ITEMS` of the items shown must name the subject, use one of the domain's event words, and be published by the deadline (an item about the subject's sport or culture is not coverage of a conflict); the judges must have been shown every on-subject item in the window, including reports from the 18-hour grace, because an item cap that dropped one could have dropped the report confirming the event; and the judgment must cite at least one of those coverage items. Subjects with more than 32 on-subject items in the window cannot seal an absence-based NO; agreement requires the same basis from both judges, and the sealed evidence records `basis` so absence-based NOs can be counted apart from proven ones. The archive that backs those citations retains **14 days**, while a judged entry requires evidence reaching back **7 days before its deadline**. An entry therefore has a hard recovery window: once `now` passes 14 days after the start of its required evidence, the evidence has aged out of the archive and no later run can retrieve it. The required evidence starts 7 days before the deadline, or at generation for a forecast generated later than that, so for 7-day and 30-day forecasts the window closes at `deadline + 7 days`.

Rather than retry such an entry until its attempt budget is exhausted, the resolver seals it deterministically as VOID with reason `beyond_archive_horizon`, and warns while entries are still inside the window so the backlog can be drained before they strand. Every judge attempt persists a structured record naming the stage it failed at (`archive`, `judge_a`/`judge_b`, `normalize`, `agreement`, `terminal`) and the failure class, which the scorecard rolls up under `judgedLane` — an internal operator block that is not served on the public scorecard endpoint — alongside first-attempt seal rate, VOID-by-reason and attempts per resolved entry. The SLA window is two days measured from the deadline plus the 18-hour reporting grace, the first moment the lane may judge, so it always holds a first attempt and one retry on the daily schedule. The SLA metric counts *scored* resolutions within the window rather than resolutions of any kind, so a lane that seals everything as an instant VOID reports a rate of zero rather than a perfect one; the VOIDs it produced are reported beside it. A `beyond_archive_horizon` VOID is cost control, not a resolution-quality result: it is counted as VOID, never as a scored resolution.

### Calibration map (shadow)

Each resolver run also maintains a calibration map in `forecast:calibration-map:v1`. The map is fitted by isotonic regression (pool-adjacent-violators) on individual resolved YES/NO published-origin forecasts from the 180-day window. It excludes `bet_engine` and `state_derived` entries, and entries with no recorded origin (filed as `unknown`), the same population as the headline skill score. Entries with no recorded origin predate origin tagging and cannot be attributed to a generator. It also excludes entries whose market anchor has no `marketBlendedProbability` lineage field. The matcher before issue #7071 chose those anchors, and it often paired forecasts with unrelated markets. The fit cohort uses the scorecard's own predicates, so it never includes a row the scorecard excludes: VOID rows (late reads and old-selection judged verdicts among them), duplicate windows, withheld state buckets, and rows rescored to their first-seen probability.

Eligibility counts families, not rows. A family is one forecast id, and its windows share a generator, a region and much of an outcome history. A domain receives a non-identity map only when its cohort has at least 30 families (`CALIBRATION_MIN_FAMILIES`), at least 10 of them with a YES outcome and at least 10 with a NO outcome (`CALIBRATION_MIN_OUTCOME_FAMILIES`). A family whose windows resolved both ways counts on both sides. A one-sided domain, such as cyber with only NO outcomes, can never fit. In a simulation on the live published-origin probabilities, a fit with fewer than 10 families on either side lost to identity on expected Brier by more than the activation gate's 0.005 margin in every miscalibration tried, so it could not plausibly pass the gate. Each domain records its family counts and, when it is identity, the `ineligibleReason`. Every other domain, and any domain the map has not seen, passes probabilities through unchanged. Fitted values are bounded to the range 1% to 99%.

The map records its version, fit time, fit window, cohort filter, per-domain sample and positives, and the probability stage it was fitted on (`marketBlendedProbability`, read from `calibration.marketBlendedProbability` when an anchor applied and from the stored `probability` otherwise). The map stays unchanged between runs so that its forward cohort can grow. Every resolver run recomputes eligibility and refits only for one of these causes, recorded as `refitReason`:

- `fit_input_withdrawn`: a row a fitted domain used was later voided, marked duplicate, rescored or re-graded to the other outcome. Each fitted domain stores its input rows under `inputs` for this check. A row pruned from the ledger, or one that only left the rolling window, is not a withdrawal.
- `fit_invalidated`: a fitted domain is no longer eligible, for example because its rows left the rolling window.
- `domain_became_eligible`: an identity domain reached the family minimums.
- `family_growth`: a fitted domain's families reached twice the count it was fitted on (`CALIBRATION_REFIT_FAMILY_GROWTH`).
- `absent`, `invalid` or `code_version_changed`: the stored map is missing, unreadable, or from another fitting rule.

A data refit increments `dataVersion` and keeps the code version. Each refit starts a new forward cohort, so a refit waits until the domain's sample has doubled. The standard error of the fit then falls by about 30%. While the activation gate passes for the stored map, growth and new eligibility do not refit: the refit would discard the forward evidence and revert a validated publication. The resolver logs the held trigger. A withdrawn input or an invalidated fit refits even then, and publication returns to raw on the next seeder run, because the gate for the new map has no forward outcomes yet. A failed read keeps the stored map instead of refitting.

The map changes published probabilities only while the activation gate below is eligible. The scorecard carries an internal `calibrationShadow` block for the forward cohort, which is the set of forecasts emitted after the map was fitted. Like `judgedLane`, the public scorecard endpoint does not serve it. For the forward cohort the block reports raw and calibrated Brier, the paired bootstrap 95% interval on their difference, expected calibration error with bootstrap intervals, and reliability buckets with Wilson intervals. Every figure shows its sample size. The evaluator refuses any entry emitted at or before the end of the fit window, so the map is never scored on the outcomes it was fitted on.

#### Activation gate

`calibrationShadow.activationGate` reports `eligible` and lists every reason it is not eligible. The gate is eligible only when all of these conditions hold:

- The forward cohort has at least 60 published-origin outcomes, and at least 30 in every domain with a non-identity map.
- The upper bound of the paired bootstrap 95% interval on calibrated minus raw Brier is at most 0.005, overall and in every non-identity domain.
- The map is monotone and has at least one non-identity domain.

Forward coverage (registered, matured, scored, VOID by reason, pending) and the generation-origin mix are reported beside the verdict, so a change in which forecasts resolve cannot read as a skill gain. The bootstrap draws 2,000 entry-level resamples from a fixed seed, so a rerun on the same ledger gives the same intervals.

#### Published calibration

Every `seed-forecasts` run applies the same rule. The run reads the map and the latest `calibrationShadow.activationGate`. It publishes calibrated probabilities only when the gate is eligible, the gate evaluated the current map version, and the kill switch is off. In every other case the run publishes raw probabilities. The rule does not read the previous mode, so a gate that fails on a later resolver run reverts publication on the next seeder run. No manual step is needed in either direction.

The map applies to the post-blend probability, after the market anchor and the domain cap. This is the stage the map is fitted on. The map applies before confidence, projections, trends, case files, narratives, and publish selection, so every surface in a run shows the same number. Trends and change summaries compare against the prior run re-expressed on the current scale, so a flip or a refit does not read as a probability move. Only published-origin forecasts move. State-derived forecasts keep their raw value, because the fit excludes them. Calibrated values are bounded to 1% and 99%, not to the market-blend domain caps, because the map is fitted on outcomes after those caps.

Publish selection ranks on the published probability, so the forward cohort that the gate scores can change in composition after a flip. The gate still compares raw and calibrated values on the same entries. Coverage and origin mix beside the verdict, and the `lastFlip` time, show when the cohort's selection rule changed.

A forecast that moves keeps its post-blend value as `uncalibratedProbability`. The value goes to the forecast history and the resolution ledger, but not to the public API. The ledger's `probability` is the published value, so the public scorecard scores what readers saw. The fit and the shadow read `uncalibratedProbability` as the raw value. Without it, the shadow would compare the published calibrated value with itself, and the gate would stay eligible after any flip.

The public API does not mark which probabilities are calibrated. No proto field carries the mode, so readers cannot tell from a forecast alone. The scorecard methodology text states this. The public scorecard scores each window on the probability published when the window opened, so after a flip its rolling-window Brier mixes forecasts published raw and forecasts published calibrated until the raw-era windows leave the window.

A map written by another code version publishes raw, as does a gate verdict whose scorecard is more than 48 hours old.

Set `FORECAST_CALIBRATION_FORCE_RAW=1` on the `seed-forecasts` service to publish raw probabilities whatever the gate says. A failed read of the map or the scorecard also publishes raw. A failed read of the previous record leaves the publication decision unchanged and skips the record write, so the stored flip history is kept.

Each run logs its mode, its reason, the map version, and the gate numbers: eligibility, forward count, the overall Brier-delta upper bound, and each activated domain's count and upper bound. A mode change logs a `FLIP` line. The run writes its decision to `forecast:calibration-publication:v1` after the publish succeeds. The record holds the mode, the reason, the gate numbers, the decision time, and `lastFlip`, which gives the time, direction, reason, and gate numbers of the most recent mode change. The resolver copies the record into the internal scorecard as `calibrationShadow.publication`. The reasons are `gate_eligible`, `gate_ineligible`, `gate_map_mismatch`, `gate_stale`, `map_code_version`, `no_gate`, `no_map`, `read_failed`, and `force_raw`.

#### Rollback to identity

Identity is the fallback at every level. An unknown domain, an identity domain, and a missing map all return the input probability unchanged. Raw publication is the fallback for the activated path: a failing gate, a missing map, or the kill switch publishes the post-blend probability on the next run. A calibrated publication keeps its post-blend value as `uncalibratedProbability`, so a return to raw loses no lineage.
